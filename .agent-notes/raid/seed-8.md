evidence: `config/scaling/devices/dev8_bs64.yaml` has no `data:` block at all; the only body keys are `optimization.grad_accum_steps: 1` (:37-38) and `logging.folder` (:40-41). The other three rungs each declare `data.batch_size` explicitly (`dev1:36` -> 512, `dev2:35` -> 256, `dev4:35` -> 128). So the 8-device rung is the only one whose micro-batch lives somewhere else, which is why its header has to explain itself (:23-26): "At this rung the per-device micro-batch is 64, which is the reference `data.batch_size`, so this file restates nothing for the batch and changes only the accumulation — an honest no-op would have left the global batch at 64 x 8."
  It is currently safe only by coincidence. `TestFixedSizeDistributedFamily` would catch a change, but via an incidental route: `test_micro_batch_strictly_decrease` (`tests/test_config_system.py:888-894`) fails on a duplicate micro-batch, and `test_global_effective_batch_is_held_fixed` (:870-886) fails on the product. Neither failure message would point at the real cause ("this rung restated its batch").
  The cost is that the family is not self-describing: reading the four files alone does not tell you the sweep axis, which is the one thing the family exists to communicate.
