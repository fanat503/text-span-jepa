# seed-10
finding: `baselines/data2vec_baseline.py` diverges from the fairseq implementation its header cites ("Directly adapted from fairseq/examples/data2vec/models/data2vec_text.py") in three places that change the loss: layer-norm is applied to the *averaged* top-K stack rather than per layer, the regression head is missing fairseq's trailing GELU, and the loss is divided by `sqrt(embed_dim)` via `loss_scale = -1` where fairseq's default `loss_scale` is 1.0.
evidence: `baselines/data2vec_baseline.py:130-131`:
  `h_target = torch.stack(target_layers, dim=0).mean(dim=0)` then `h_target = F.layer_norm(h_target.float(), h_target.shape[-1:])`.
  The normalisation is therefore a single `layer_norm` over the mean of the top-K, so layers with larger activation scale dominate the average *before* normalisation. fairseq normalises each candidate layer (`normalize(x) = F.layer_norm(x, x.shape[1:])`) and then selects and averages the top-K, so the average is taken over normalised tensors. The two orders give different targets whenever the per-layer scales differ — which is exactly the quantity `average_top_k_layers` exists to exploit.
  `:90-91` — `projs.append(nn.Linear(curr_dim, embed_dim))` ends the head with a bare `Linear`. fairseq's `LinearHead` is `[Linear(d, 2d), GELU, Linear(2d, d), GELU]`, so this implementation applies the activation *before* the last projection instead of after.
  `:60-62,159-160` — `loss_scale: null` in `defaults.yaml:266` becomes `self.loss_scale = -1` (`:60-63`), and `:159-160` then does `loss_total = loss_total / math.sqrt(sz)`. The default denominator is therefore `sqrt(embed_dim)` (e.g. 27.7 at 768), not 1.
  None of this is a crash and none of it is self-evidently wrong for a baseline; it is a fidelity question that needs a human to decide, which is why it is filed as a seed and not a patch. `head_layers: 2` is correctly forwarded by `src/train.py:514` and matches fairseq's default.
