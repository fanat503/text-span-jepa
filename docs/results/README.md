# `docs/results/` — the results section, built to not lie

This directory holds the paper's results apparatus. It exists because the repo
had 1910 green tests, 25 closed defects, and **zero results**: training is
forbidden on the agent machine and the GPU belongs to the owner. Everything here
is computable without training, so the only thing left is the run itself.

The four files are generated by one script. Do not hand-edit them.

| file | what it is |
|---|---|
| `TABLES.md` | Tables A and B — the main and ablation results, cells filled from run artifacts |
| `COST.md` | Table C — the wall-clock cost model, with its arithmetic and its unknowns |
| `RUN_PLAN.md` | the owner's run order, one command per run |
| `param_counts.json` | measured parameter counts for all 62 configs, content-addressed |

```powershell
$PY = "C:\Users\Илья\AppData\Local\Programs\Python\Python310\python.exe"
& $PY scripts/results_apparatus.py table  --out docs/results/TABLES.md
& $PY scripts/results_apparatus.py cost   --out docs/results/COST.md
& $PY scripts/results_apparatus.py howto  --out docs/results/RUN_PLAN.md
& $PY scripts/results_apparatus.py verify          # the guard; run this in CI
```

`README.md` (this file) is the only hand-written one.

> **`.gitignore` note.** The repo's `.gitignore` line 50 is `results/`, which git
> matches against *any* directory of that name at any depth — so it also hides
> `docs/results/`. These four files are tracked with `git add -f` and are
> committed. A regeneration that adds a new file here needs `-f` too, or git will
> silently ignore it and the file will look like it was never produced.

## The one rule

**No number in these tables was modelled, extrapolated or interpolated.**

A results table whose empty cells look plausible is worse than no table, because
the owner cannot tell a real result from a placeholder at a glance. That is the
exact failure this campaign exists to prevent, and it is the failure a
well-meaning agent produces when it helpfully fills in a plausible `0.83`.

So every cell is one of exactly two things:

| marker | meaning |
|---|---|
| `NOT-RUN` | a run would produce this number, and no run has |
| `NOT-APPLICABLE` | **no run of that config could ever produce it** |

Both are words. Neither is a digit, a dash, a blank, `N/A`, or `?`. A dash in a
results table reads as zero to everyone who has ever read one; a question mark
invites the reader to supply their own guess. `scripts/results_apparatus.py`
keeps the list of refused markers in a `REFUSED_MARKERS` dict, each with the
reason it is refused, and `verify` asserts none of them reaches the output.

### The guard is structural, not a convention

`Cell` holds either a measured string or a reason. `Cell.render()` returns the
marker and **ignores** its text argument whenever the cell is unmeasured, so
there is no argument you can pass that reaches the output as a fabricated
number. `assert_marker_honest()` runs before anything is printed, and
`guard_selftest()` then tries twelve ways to get a number past it — a zero, an em
dash, a minus, a bare dot, `N/A`, `12.5` — and fails `verify` if any of them
succeeds. A check never observed to fail is indistinguishable from a check that
cannot fail, so `verify` reports the self-test count in its own output.

## What is already measured, with nothing run

Parameter counts. All 62 configs, exactly, by constructing the model
`src.train.create_model` builds from the deep-merged config and summing
`numel()` over `requires_grad`. This is a real measurement, not an estimate, and
it needs no GPU: models are built on meta tensors where that works, and on CPU
where it does not. Cached in `param_counts.json`, keyed by
`sha256(defaults.yaml + the config)`, so editing either invalidates that row and
nothing else — a cache keyed on filename would go stale silently, which is the
same failure mode as a stale results table.

The scaling ladder, measured:

| config | trainable | total |
|---|---|---|
| `xsmall_30m` | 32.3M | 62.5M |
| `small_100m` | 88.9M | 170.7M |
| `base_140m` | 137.9M | 262.0M |
| `large_300m` | 284.4M | 538.0M |

## What a run fills in

Every other cell comes from files `src/train.py` writes into `logging.folder`:

| artifact | what it carries |
|---|---|
| `train_log.csv` | 12 columns, logged every `logging.log_freq` iterations |
| `checkpoint-ep{N}.pth.tar` | one per completed epoch — the **N is the epoch**, so run progress is read off the filenames |
| `best.pt` | `extra.best_val_loss` |
| `params-text-span-jepa.yaml` | the merged config the run actually used |

There is no results file to keep in step by hand. The tables are a pure function
of *(configs on disk, run artifacts on disk)*, so a stale table is not a state
this apparatus can be in.

`--run-root` maps `logging.folder: output/...` onto another root, so results on an
external drive need no config edits.

## Four traps in the trainer that a naive table walks into

These are why the apparatus gates cells on the *resolved config* rather than
trusting the CSV.

**1. A `0.000000` in `train_log.csv` may mean "absent", not "zero".**
`src/train.py:1556-1569` fills every missing key with `0`, and
`src/models/jepa.py:650` emits `decoder_accuracy: 0.0` on an early-return path.
So `no_decoder_loss.yaml` and `none.yaml` would report a decoder accuracy of
exactly zero, which reads as a measurement. Any column whose `lambda_*` weight is
`0` in the resolved config renders `NOT-APPLICABLE` instead.

**2. The baseline arms populate none of the loss-component columns.**
Measured: `baselines/mlm_baseline.py:203` returns `{"loss_mlm", "mlm_accuracy"}`
and `baselines/data2vec_baseline.py:189` returns `{"loss_data2vec", "ema_decay",
"num_masked"}`. Neither mentions `loss_span`, `loss_decoder`, `decoder_accuracy`
or any VICReg term, so trap 1 applies to *every* baseline row. Those cells are
`NOT-APPLICABLE`.

**3. Validation loss is in no CSV at all.** It goes to stdout
(`src/train.py:1606`) and to `best.pt`'s payload. The paper's headline column
therefore cannot be assembled from `train_log.csv`, and it stays `NOT-RUN` with
the extraction command in the cell's provenance — never back-filled from the
training loss, which is a different quantity.

**4. The three arms' `loss` values are not comparable.** JEPA span loss, MLM
cross-entropy and data2vec regression are three different objectives. `loss` is
the only column every arm populates, and it does **not** rank the arms against
one another.

### What the paper still does not have

No representation-quality number. `src/eval/probes.py` has a working
`LinearProbe`, but nothing in `src/train.py` calls it, so **no run this repo can
currently produce emits a downstream metric**. The paper's central claim is about
representation quality, and that column cannot be filled by any config in
`config/`. Wiring the probe in is a `src/train.py` change and belongs to that
file's owner; it is flagged here rather than quietly papered over with a proxy.

## The wall-clock estimate

`COST.md` is arithmetic over four config-derived terms (exact) and two measured
ones. Both measured ones render `NOT-RUN` until supplied, because a wall-clock
figure resting on a guessed corpus length or a guessed GPU throughput is
precisely the kind of plausible number that reads as a measurement.

Supply them like this:

```powershell
# train_seqs: a property of the corpus on the owner's disk
& $PY -c "from src.datasets.kaggle import load_wikitext103 as L; d,_=L('gpt2',512,'train',r'data/wikitext-103'); print(len(d))"

# seconds per epoch: free, from the run that was going to happen anyway.
# src/train.py:1591 already prints 'Epoch N avg loss: ... time: Ns' every epoch.
& $PY -m src.train --fname config/scaling/xsmall_30m.yaml 2>&1 | Tee-Object run.log

& $PY scripts/results_apparatus.py cost --log-file run.log --train-seqs N
```

**The attribution is strict, and that is the point.** One run's
seconds-per-epoch is applied only to configs whose *measured trainable parameter
count* matches what that run's log reported (`src/train.py:1177`). The first
version of this table applied one timing to every row — it printed `5.7 h` for
`large_300m` from a measurement taken on `xsmall_30m`, and labelled the column
"never extrapolated between models" while doing exactly that. A wall clock for a
model nobody ran is a fabricated result with a real-looking provenance string.
To fill in a larger model, run one epoch of it and hand the table that log.

## Figures

`curves` draws from `train_log.csv` only:

```powershell
& $PY scripts/results_apparatus.py curves --out-dir docs/results/figures
```

With no run on disk it writes **no PNG** and prints `NOT-RUN` per config. Empty
axes with a flat line look like a result, so nothing is drawn on purpose.
